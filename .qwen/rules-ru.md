# Инструкции для Qwen — Heroes of Might and Magic: Арена

> **Внимание:** Это русскоязычная копия основных инструкций из `.qwenrules`.
> Для работы используется только файл `.qwenrules`. Этот файл — исключительно для вашего понимания.

## Политика сервера разработки

- НЕ запускать автоматически dev-серверы (npm run dev, vite и т.д.) после изменений
- Пользователь будет вручную запускать и тестировать проект
- Запускать только команды сборки (`npm run build`, `tsc --noEmit`) для проверки компиляции

## Обзор проекта

- **Цель:** Создать клон Heroes of Might and Magic (в стиле HoMM3)
- **Стартовая точка:** Режим «Арена» — пошаговая тактическая битва
- **Технологии:** TypeScript, PixiJS, Vite

## Основные правила режима «Арена»

- Две стороны (атакующий и защитник)
- Каждая сторона имеет от 1 до 7 отрядов существ
- Гексагональная сетка на поле боя (как в HoMM3)
- Порядок ходов определяется инициативой существ
- Существа перемещаются и действуют в порядке очереди

## Стандарты кода и архитектура

### Организация файлов

```
src/
├── types/          # TypeScript интерфейсы и типы
├── core/           # Игровой движок, управление состоянием
├── entities/       # Классы существ
├── ui/             # UI компоненты (панели, HUD)
├── grid/           # Логика гексагональной сетки
├── combat/         # Боевая система, расчёт урона
├── ai/             # Логика AI
└── main.ts         # Точка входа
```

### Стандарты кодирования

- TypeScript strict mode
- Интерфейсы для типов данных, классы для игровых сущностей
- Компоненты маленькие и с одной ответственностью
- Лучшие практики PixiJS (пул объектов, иерархия контейнеров)
- Комментировать сложную игровую логику (формулы урона, порядок ходов)
- Использовать константы для значений баланса (диапазоны урона, дальность хода)

### Принципы архитектурытуры

- Data-driven: характеристики существ определены в конфиг-объектах, не захардкожены в классах
- Event-driven: PixiJS EventEmitter для игровых событий (урон нанесён, ход сменился)
- State machine: состояния боя (IDLE, MOVING, ATTACKING, ANIMATING, GAME_OVER)
- Разделение логики и рендеринга: состояние игры → пайплайн рендера

### Алгоритм очереди ходов (Финальный)

Панель очереди ходов использует **фиксированный массив из 12 слотов** со следующим алгоритмом сдвига:

- **Инициализация (`init`)**: Строит слоты из уникальных стеков, отсортированных по инициативе: `[Лучник, К1, К2, К3, R2, Лучник, К1, К2, К3, R3, Лучник, К1]`
- **Обычный ход (`advanceTurn`)**: `shift()` первого слота → если это стек, `push(actingStack)` в конец; если метка раунда, `push(следующая метка)`
- **Ожидание (`advanceTurnWithWait`)**: `shift()` первого слота → если это стек, вставить ожидающий стек **перед первой меткой раунда** (конец текущего раунда); если удалена метка — добавить новую
- **Новый раунд (`reinit`)**: Полная пересборка очереди с правильным номером раунда
- **Гибель (`removeStack`)**: `filter` — удалить все копии мёртвого стека из слотов

Ключевые файлы:

- `InitiativeQueue.ts` — управляет порядком ходов, `next()`, `moveToEnd()` для Wait
- `TurnOrderPanel.ts` — визуальная панель из 12 слотов, алгоритм shift/push
- `ActionManager.ts` — отслеживает флаг `isWaiting` для каждого стека
- `BattleScene.ts` — оркестрация: `handleTurnEnded(actingStack)` проверяет `isWaiting` до вызова `next()`

Поведение Wait:

1. Игрок нажимает Wait → `ActionManager.wait()` → `InitiativeQueue.moveToEnd(stack)` + `state.isWaiting = true`
2. `endTurn(stack)` эмитит событие → `BattleScene.handleTurnEnded(stack)` получает стек напрямую из события
3. `wasWaiting = actionManager.isWaiting(actingStack)` проверяется ДО `initiativeQueue.next()`
4. Панель: `advanceTurnWithWait(actingStack)` → shift + вставка перед первой меткой раунда
5. Новый раунд: `resetAllActions()` очищает флаги `isWaiting`, `reinit()` перестраивает очередь с начала

## Правила рабочего процесса

- Реализовывать по одной фазе за раз, спрашивать подтверждение перед переходом к следующей
- После каждого значимого изменения запускать `tsc --noEmit` для проверки компиляции
- НЕ добавлять placeholder-ассеты — использовать простые геометрические фигуры или цветную графику до предоставления реальных ассетов
- Игра должна быть играбельной на каждом шаге (инкрементальная разработка)
- Спрашивать пользователя перед принятием значительных архитектурных решений
- **После каждого изменения `.qwenrules` (бестиарий, правила и т.д.) — дублировать обновлённый контент в `.qwen/rules-ru.md` на русском языке**
- **Придерживаться единого стиля документирования в `.qwenrules` и `.qwen/rules-ru.md`:**
  - Чеклисты фаз используют формат `- [x]` / `- [ ]` (например, `- [x] 2.2 Атака: ...`)
  - Секции «Реализовано в фазе X.Y» используют маркированные списки с вложенными подпунктами

## Существа на несколько гексов

Некоторые существа (например, Грифон) занимают **2 гекса** на поле боя. Это управляется параметром `sizeInHexes` в `CreatureConfig`:

- `sizeInHexes: 1` (по умолчанию) — существо занимает 1 гекс, обычный размер
- `sizeInHexes: 2` — существо занимает 2 соседних гекса, отрисовывается как прямоугольник, охватывающий оба гекса

**Реализация:**

- `CreatureStack.getSizeInHexes()` — возвращает размер существа в гексах
- `CreatureStack.getOccupiedHexes()` — возвращает массив всех гексов, занимаемых стеком
- `CreatureStack.getOccupiedHexesAt(targetHex)` — возвращает гексы, которые занимал бы стек на указанной позиции (без фактического перемещения)
- `CreatureStack.occupiesHex(hex)` — проверяет, занимает ли стек указанный гекс
- `BattleManager.getOccupiedHexes()` — агрегирует занятые гексы от всех стеков (исключая указанный)
- `BattleManager.canStackMoveTo()` — проверяет, может ли стек встать на позицию (все гексы свободны и в пределах поля)
- `BattleManager.getStackAtHex()` — находит стек, занимающий указанный гекс
- Поиск пути (BFS) считает все занятые гексы препятствиями
- **Перемещение**: для многогексовых существ:
  1. Собственные занятые гексы существа добавляются в список заблокированных (чтобы оно не могло переместиться на свои собственные гексы)
  2. Доступные гексы фильтруются — остаются только позиции, где помещается вся фигура
  3. Pathfinding проверяет каждую позицию на пути — существо перемещается как единое целое, а не по одному гексу
  - Пример: Грифон на [8,2]-[9,2] может переместиться на [10,2]-[11,2], но НЕ на [9,2]-[10,2] (это был бы сдвиг на 1 гекс, перекрывающийся с собственной позицией)
- Визуальная отрисовка: существа на 2 гекса рисуются как прямоугольник (`rect`), охватывающий оба гекса, центрированный между ними
- Hit area: расширенный прямоугольник, покрывающий оба гекса, чтобы клик на любой из них выделял существо

**Ключевые файлы:**

- `CreatureStack.ts` — `getOccupiedHexes()`, `getOccupiedHexesAt()`, `occupiesHex()`, `moveTo()` с проверкой footprint
- `BattleManager.ts` — `getOccupiedHexes()`, `canStackMoveTo()`, `getStackAtHex()`
- `HexGridInteraction.ts` — `getReachableHexes()` добавляет собственные гексы в blocked list для многогексовых существ
- `HexUtils.ts` — `findPath()` и `findHexStepPath()` принимают опциональный коллбэк `isValidPosition`

## Расстановка стеков на поле

- **Размер сетки:** 12×10 гексов (width=12, height=10)
- **Игрок (атакующие):** размещаются в левой части поля, сверху вниз (q=0..2, r=0..N)
- **Враг (защитники):** размещаются в правой части поля, начиная с q=11, сверху вниз (r=0..N)
- Каждый следующий стек получает следующую свободную позицию вниз по сетке

### Координаты размещения стеков атакующей стороны (5 стеков)

- Массив координат (`attackerPlacementHexes` в `main.ts`):

| Стек # | q   | r   |
| ------ | --- | --- |
| 1      | 0   | 0   |
| 2      | -1  | 2   |
| 3      | -2  | 4   |
| 4      | -3  | 6   |
| 5      | -4  | 8   |

- **Закономерность:** Каждый следующий стек сдвигается влево на 1 (q-1) и вниз на 2 (r+2)
- **Использование:** `attackerPlacementHexes[i]` возвращает гекс для стека с индексом `i` (0-based)

### Координаты размещения стеков защищающейся стороны (5 стеков)

- Массив координат (`defenderPlacementHexes` в `main.ts`):

| Стек # | q   | r   |
| ------ | --- | --- |
| 1      | 11  | 0   |
| 2      | 10  | 2   |
| 3      | 9   | 4   |
| 4      | 8   | 6   |
| 5      | 7   | 8   |

- **Закономерность:** Зеркальное отражение стеков атакующих по вертикальной оси
- **Формула зеркала:** `q_defender = q_min(r) + q_max(r) - q_attacker` для каждой строки `r`
  - Строка r=0: q_min=0, q_max=11 → зеркало q=0: 0+11-0=11
  - Строка r=2: q_min=-1, q_max=10 → зеркало q=-1: -1+10-(-1)=10
  - Строка r=4: q_min=-2, q_max=9 → зеркало q=-2: -2+9-(-2)=9
  - Строка r=6: q_min=-3, q_max=8 → зеркало q=-3: -3+8-(-3)=8
  - Строка r=8: q_min=-4, q_max=7 → зеркало q=-4: -4+7-(-4)=7
- **Использование:** `defenderPlacementHexes[i]` возвращает гекс для стека с индексом `i` (0-based)
